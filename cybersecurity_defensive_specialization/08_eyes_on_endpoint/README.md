# Eyes on Endpoint

> "You can't protect what you can't see." — SANS Institute, Blue Team Operations Motto

## Introduction

Two projects of hardening. billing-srv-01 scores 84 on Lynis. The Windows domain has Sysmon, locked passwords, AES-only Kerberos, SMBv1 dead, AppLocker in audit mode. The attack surface is smaller. The walls are thicker.

But walls do not tell you when someone is climbing them.

Hardening reduces what an attacker CAN do. Telemetry reveals what an attacker IS doing. The hospitals in the Crimson Tide advisory had firewalls and antivirus. What they did not have was visibility. The attacker lived inside their networks for 4-7 days, harvesting credentials, mapping infrastructure, exfiltrating databases and destroying backups. Nobody saw it. Nobody alerted. Nobody responded. Because nobody was watching.

This project makes every endpoint at MedDefense observable. You will validate, refine and export the telemetry generated by the instrumentation you deployed, PowerShell Script Block Logs, auditd records, auth.log entries. You will run controlled attacker simulations against your own hardened endpoints and prove that your instrumentation captures every action. You will assess coverage gaps, quantify telemetry quality and produce a structured export package that becomes the analyst's evidence in Module 3.

This is the bridge between building defenses and observing their effects. The telemetry you export here is the raw material the SOC consumes.

## Why this matters

Hardening, was about making MedDefense harder to break into. Telemetry engineering (this project) is about knowing when someone breaks in anyway. Because they will. No hardening is perfect. The Crimson Tide attacker exploited a zero-day on the FortiGate, a device you cannot harden with CIS benchmarks. The first line of defense failed. Without visibility, there is no second line. The telemetry you produce here feeds every downstream.

## Context

Week eight at MedDefense Health Systems. Monday morning.

Robert Kim (Infrastructure Lead) reviews the status board. Linux: hardened. Windows: hardened. Firewall: not yet. Patch management: not yet. Endpoint visibility: unknown.

"The hardening is solid. auditd is running. Sysmon is deployed. PowerShell logging is on. But I cannot tell you if these tools are actually seeing what matters. Are we generating the right events? Are there gaps in coverage? If an attacker bypasses the hardening, will we know?"

He turns to you.

"Your job is to make these endpoints defensible, not just defended. That means: validate that every security-relevant action produces a trace. Run the attacker's playbook against your own systems and prove the instrumentation catches it. Then package all of it for the SOC. Because next week, you become the analyst, and you need to trust the data you built."

James Chen adds: "And when you export the telemetry, I need it structured. JSON. Normalized timestamps. Consistent fields. The SOC cannot work with raw log files in 15 different formats. Build the evidence package the way you would want to receive it as an analyst."

## Learning Objectives

By the end of this project, you are expected to be able to explain to anyone, without the help of Google:

### Endpoint Telemetry Engineering

- How Sysmon Event IDs map to attacker behavior: process creation, network connections, image loads, process access, file creation, registry modification, DNS queries
- How PowerShell Script Block Logging captures decoded command content, why Module Logging and Transcription complement it, and what each reveals
- How auditd rules generate kernel-level audit records for file access, privilege escalation, process execution and network socket creation
- How to validate telemetry coverage by running controlled simulations and measuring detection completeness
- The difference between visibility and protection, and why both are necessary

### Telemetry Quality and Export

- How to assess telemetry quality: event type distribution, time coverage, field completeness, gap detection
- How to export Windows events and Linux logs to structured JSON with normalized timestamps and consistent fields
- How to produce a telemetry handoff package suitable for analyst consumption

### Attack Simulation and Validation

- How to run controlled attacker-like actions (process creation, network connections, file operations, registry modifications, privilege escalation) safely against a hardened endpoint
- How to correlate a ground truth attack log against captured telemetry to produce a detection matrix
- How to identify and document coverage gaps using MITRE ATT&CK technique mapping

## Requirements

### General

- A `README.md` file, at the root of the folder of the project, is mandatory.
- All your files should end with a new line.

### Scripting

- Bash scripts must start with `#!/bin/bash` and pass shellcheck.
- PowerShell scripts must have the `.ps1` extension and use `Set-StrictMode -Version Latest`.
- All scripts must include a comment header with: name, purpose, author.
